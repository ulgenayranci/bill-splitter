## Issue 1: Move item editing to its own screen; the scanned bill review container gets Retake + Edit
Severity: high · Effort: L · Category: layout / interaction · Location: `components/wizard/SetupStep.tsx`
Viewport: mobile · Author: user · Source: `review-20260929-scanreview:dictated_001`, `2501a54c-43fb-4c90-8678-1d6a0a4ecb25:note_002` ("move up", pinned on the receipt photo), drawings `draw_001`–`draw_020` (container outline + two side-by-side button sketches labelled roughly "reta…" and "Edit")

### Problem
User's words: *"ok we are adding one more screen then. this way the interface is too complicated. remove the yellow edit area from this step and lets add an edit button next to the retake button. use the button defsault style of the app. lets call this container as scanned bill review container."*

Today, a mismatched scan shows a long yellow list (name row + price/qty/delete row per item, "Add item", and the "off by" line) above the photo card. With 6 items it fills more than a phone screen and pushes the photo and the people section far down.

### Direction (user decisions, 2026-09-29)
- **Remove** the yellow list (`data-testid="scan-review"`) from the setup step.
- **Scanned bill review container** = the photo card: receipt photo, "N items found" badge, and a button row with **Retake** and a new **Edit** button side by side (as sketched). With the yellow list gone, the container moves up, which covers the "move up" note.
- **New screen** for editing scanned items. It keeps the same capabilities as today: edit name/price/qty, delete, add item, and the live "Items add up to … · Receipt subtotal … · off by …" check.
- **Mismatch:** when a scan doesn't add up to the receipt total, open the new edit screen **automatically**. Clean scans stay on the setup step.
- **Edit** opens the same screen at any time after a scan (mismatch or not). Leaving it returns to the setup step with changes kept.

### Suggested implementation
- The store already has an unused step number (`step: 1 | 2 | 3 | 4`; the UI uses 1, 3 and 4, and `WizardShell` maps steps to the progress strip). The new screen could use step 2 or a sub-view of step 1. **The planner decides.** The progress strip should stay 3 segments, with the edit screen counting as Setup.
- Move the existing review rows (the two-row layout shipped in 711dc36), "Add item" and the gap line into the new screen component. Reuse the `reviewDrafts` / `commitRow` logic instead of rewriting it.
- The new screen needs a clear way back (e.g. a "Done" / back action). The user hasn't specified one, so keep it minimal and consistent with the app's existing back pattern.

### Acceptance check
At 375px, after a mismatched scan:
- The edit screen opens by itself and shows every item's full name, price and qty, plus Add item and the off-by line.
- After returning, the setup step shows **no** yellow list. The scanned bill review container sits directly under "Split any bill in seconds.", with Retake and Edit side by side.
- Tapping Edit reopens the edit screen with the current values.
- After a clean scan, the setup step shows the container, and Edit is still available.
- Retake still opens the camera/picker, as it does today.

### Decision: button style (settled 2026-09-29: **(b) `outline` for both, Retake becomes a button**)
The user said *"use the button default style of the app"*. In `components/ui/button.tsx` the `default` variant is the **filled coral primary**, and `UI-SPEC.md` reserves it for "the one primary CTA" per screen. Two coral buttons (Retake + Edit), plus the coral "Start splitting / Confirm & continue" button, would break that rule. Choose:
- (a) `default` for both, exactly as said (breaks the one-coral-CTA rule), or
- (b) `outline` for both (the spec's "secondary actions" style, recommended), or
- (c) `default` for Edit only, and `outline` for Retake.
Also: should Retake change from its current coral text link into a button with the same style as Edit? The sketch draws both as boxes, so this assumes **yes**.

## Issue 2: Double the receipt photo height
Severity: medium · Effort: S · Category: interaction · Location: "View bill photo" button inside the scanned bill review container
Viewport: mobile · Author: user · Source: `review-20260929-scanreview:dictated_002`

### Problem
User's words: *"also lets double the hight of img.h-full.w-full this way it is not understood that it is expandable."*
Measured: the photo frame is `h-24` (96px) with `object-cover`, so only a thin strip of the receipt shows. It is already a button that opens the full photo (lightbox), but it doesn't look tappable.

### Suggested implementation
`components/wizard/SetupStep.tsx:481`: frame `h-24` → `h-48` (96px → 192px). Keep `object-cover`, the badge and the lightbox behaviour.

### Acceptance check
At 375px the photo frame is 192px tall, shows noticeably more of the receipt, and tapping it still opens the full photo.

## Issue 3: Edit screen survives a page refresh
Severity: medium · Effort: M · Category: bug / interaction · Author: ai (proposed in chat, user did not object) · Source: observed during review (a refresh wiped the review list)

### Problem
The "off by" data (`guardrail`) is React state in `SetupStep`, so a refresh loses it, and with it any mismatch warning, while the items themselves persist (`easy-billsy-bill` in localStorage).

### Suggested implementation
Persist what the edit screen needs (the receipt target total, and whether a mismatch was flagged) in the bill store, next to the items, so a refresh on the edit screen returns to it with the off-by line intact.

### Acceptance check
At 375px, on the edit screen after a mismatched scan, a refresh returns to the edit screen with the same items and the same off-by line.
